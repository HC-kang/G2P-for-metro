# Even G2 서울 지하철 플러그인 — 설계

작성일: 2026-09-20 (2차 개정: GPS 출발지 + 도착지 목록 + 워커 프록시)
상태: 승인됨

## 1. 목적

Even Realities G2 글래스에서 수도권 지하철을 안내한다. 주전장은 "탑승 중 동행"이다.
열차를 탄 뒤 남은 정거장, 환승 시점, 하차 시점을 안내한다.

## 2. 합격 기준

기존 앱의 불만에서 뽑았다.

1. 화면에 정보 위계가 있다. 줄바꿈으로만 나열하지 않는다.
2. 앱이 "지금 알아야 할 한 가지"를 먼저 말한다. 사용자가 읽고 고르게 하지 않는다.
3. 표시하는 위치는 추측이 아니라 관측이다. 관측이 아닐 때는 화면이 그렇게 말한다.
4. 환승 없는 1회 이용에 탭 3회를 넘지 않는다.

## 3. 사용자 흐름

```
앱 열기
  │  GPS로 가까운 역을 찾는다
  ▼
[출발역]  가까운 역 3~8개 + 최근 출발역        ← 탭 1회 (맞으면 첫 항목)
  ▼
[도착지]  폰에 저장한 자주 가는 도착지          ← 탭 1회
  │  경로를 계산하고 화면에 보여준다
  ▼
[열차]    그 방향 도착 예정 열차와 남은 시간     ← 탭 1회 (후보 1대면 생략)
  ▼
[동행]    남은 정거장 · 환승 · 하차 안내         ← 탭 0회
  ▼
환승역에 닿으면 [열차]로 돌아간다               ← 탭 1회
```

환승이 없으면 탭 2~3회다. 탑승 뒤에는 조작이 없다.

## 4. 결정 사항

| 결정 | 선택 | 근거 |
|---|---|---|
| 위치 추적 | 열차번호(`trainNo`) 역추적 + 관측 속도 fallback | 실제 위치를 안다. 지연과 급행을 반영한다 |
| fallback | 정적 소요시간표를 안 쓴다. 그 열차의 관측 속도를 쓴다 | 소요시간 API가 `ERROR-500`이다. 관측값이 더 정확하고 코드가 짧다 |
| 경로 계산 | 역 인접 그래프의 다익스트라. 환승 1회 = 5정거장 | 순환선·지선·분기·환승을 한 가지 방법으로 푼다 |
| 출발역 | GPS로 후보를 뽑고 사용자가 탭으로 확정 | 지하에서 GPS가 죽지만, 출발역 고르기는 지상에서 한 번만 한다 |
| 도착지 | 폰에 자주 가는 도착지만 저장 | 경로를 저장하지 않는다. 그때그때 계산한다 |
| 네트워크 | Cloudflare Worker 프록시 1개 | 서울 API가 http 전용이다. 워커가 https와 키 보관을 맡는다 |
| API key | 워커 secret. 폰에는 키가 없다 | 설정 화면에서 키 입력란이 사라진다 |
| 화면 위계 | 테두리 있는 텍스트 컨테이너 3개 + 여백 + 문자 진행 막대 | G2는 폰트 크기를 바꿀 수 없다 |

### 이미지 렌더링으로 교체하는 기준
실기기에서 상자 3개 화면을 보았을 때, 팔을 뻗은 거리에서 역 이름을 한 번에 읽지 못하면
역 이름만 이미지 컨테이너(288x144)로 바꾼다. 그 외에는 바꾸지 않는다.

## 5. 데이터 소스 (2026-09-20 실측)

### 5.1 키가 두 개다
- 열린데이터광장 **일반 인증키**는 `openapi.seoul.go.kr:8088`에서만 통한다.
  실시간 도메인에 쓰면 `ERROR-338 해당 인증키로는 실시간 서비스를 사용할 수 없습니다`다.
- **실시간 키**는 별도 신청이다. 런타임에 쓰는 것은 실시간 키뿐이고, 워커가 들고 있다.
- `sample` 키는 1~5번 항목만 준다. 오프셋을 옮겨도 `ERROR-335`다.

### 5.2 실시간 열차 위치 (런타임)
```
GET http://swopenapi.seoul.go.kr/api/subway/{RT_KEY}/json/realtimePosition/0/200/{노선명}
```
- 필드: `trainNo`, `statnNm`, `updnLine`(0=상행/외선, 1=하행/내선),
  `trainSttus`(0=진입, 1=도착, 2=출발), `statnTnm`(종착역), `directAt`(급행), `recptnDt`.
- 실측: 열차 `2301`이 약 1분 사이 잠실새내 → 잠실로 이동했다. 열차 단위 추적이 된다.
- 커버리지: 2호선 37대, 9호선 26대, 신분당선 12대, 수인분당선 32대, 경의중앙선 23대.

### 5.3 실시간 도착 정보 (런타임)
```
GET http://swopenapi.seoul.go.kr/api/subway/{RT_KEY}/json/realtimeStationArrival/0/40/{역명}
```
- 필드: `btrainNo`, `barvlDt`(남은 초), `arvlMsg2`, `trainLineNm`, `btrainSttus`, `subwayId`.
- **함정**: `updnLine`을 `"상행"`/`"하행"`으로 준다. 위치 API는 `"0"`/`"1"`로 준다. 정규화가 필요하다.

### 5.4 역 목록 (빌드 시 1회)
```
GET http://openapi.seoul.go.kr:8088/{KEY}/json/SearchSTNBySubwayLineInfo/1/800/
```
799개역. 필드 `STATION_NM`, `LINE_NUM`("01호선"), `FR_CODE`.

#### `FR_CODE` 구조
숫자만 뽑으면 안 된다. `P142`(가산디지털단지)와 `142`(구일)가 충돌한다.
1호선 20건, 5호선 7건, 경의선 2건이 겹쳤다. 세 꼴이 있다.

| 꼴 | 예 | 뜻 |
|---|---|---|
| `NNN` | `142` 구일 | 본선 |
| `XNNN` | `P142` 가산디지털단지 | 알파벳 분기. 1호선 경부선, 5호선 마천지선 |
| `NNN-M` | `211-1` 용답 | `NNN`번 역에서 갈라지는 지선. 2호선 성수지선 |

`{ branch, order }`로 쪼개면 `line + branch + order`가 유일하다. 빌드 시 검증한다.

### 5.5 역 좌표 (빌드 시 1회)
```
GET http://openapi.seoul.go.kr:8088/{KEY}/json/subwayStationMaster/1/1000/
```
784개역. 필드 `BLDN_NM`, `ROUTE`, `LAT`, `LOT`.
역 목록의 고유 이름 655개 중 647개가 매칭된다. 안 되는 8개는 최근 개통역이다
(운정중앙, 평택지제, 시우, 자양, 한국항공대, 용인중앙시장, 4·19민주묘지, 서해구청).
좌표가 없는 역은 GPS 후보에 안 나온다. 최근 출발역으로 고른다.

### 5.6 G2 위치 API
SDK가 정식 지원한다. `app.json`의 `location` 권한이 실재한다
(CLI 스키마 실측: `g2-microphone`, `phone-microphone`, `album`, `location`, `network`, `camera`).

```ts
bridge.getAppLocation(opts): Promise<AppLocation>
bridge.startAppLocationUpdates(opts) / stopAppLocationUpdates()
bridge.onAppLocationChanged(cb)
AppLocation = { latitude, longitude, accuracy?, altitude?, speed?, heading?, timestamp? }
AppLocationAccuracy = 'low' | 'medium' | 'high'
```

## 6. 워커

Cloudflare Worker 1개가 프록시다. 경로는 둘뿐이다.

| 경로 | 대상 |
|---|---|
| `GET /position/{노선명}` | `realtimePosition/0/200/{노선명}` |
| `GET /arrival/{역명}` | `realtimeStationArrival/0/40/{역명}` |

- 실시간 키는 Worker secret `SEOUL_RT_KEY`다. 클라이언트에 없다.
- 요청 헤더 `X-Metro-Token`을 secret `METRO_TOKEN`과 비교한다. 불일치면 403이다.
- 응답에 `Access-Control-Allow-Origin: *`와 `Access-Control-Allow-Headers: x-metro-token`을 준다.
- 그 밖의 경로는 404다. 임의 URL을 중계하지 않는다.

**한계를 인정한다.** 토큰은 앱 번들 안에 있으므로 꺼낼 수 있다.
이것은 우연한 남용을 막는 장치이지 인증이 아니다. 개인용이라 이 수준으로 충분하다.
남용이 보이면 Cloudflare rate limit을 건다.

무료 한도는 하루 10만 요청이다. 10초 polling으로 하루 왕복 2시간을 써도 720회다.

## 7. 구조

| 파일 | 책임 |
|---|---|
| `worker/index.js`, `worker/wrangler.toml` | 프록시 |
| `scripts/fetch-stations.mjs` | 빌드 전 1회. `src/stations.json` 생성 |
| `src/stations.json` | 역 + 지선 + 좌표 + 노선 ID 정적 데이터 |
| `src/stations.ts` | 인접 그래프, 좌표 조회, 환승 판정, subwayId → 노선명 |
| `src/route.ts` | 다익스트라 경로, 방향, 남은 정거장, 속도, 추정 위치 |
| `src/geo.ts` | 좌표 → 가까운 역 목록 |
| `src/screen.ts` | 화면 문자열 생성과 바이트 한도 적합 |
| `src/api.ts` | 워커 호출과 응답 정규화 |
| `index.html` | 폰 설정 화면. 자주 가는 도착지만 |
| `src/main.ts` | 상태 기계와 G2 SDK 호출 |
| `app.json` | Even Hub 매니페스트 |

`route.ts`, `geo.ts`, `screen.ts`는 네트워크와 SDK에 의존하지 않는다. 그래서 단독으로 테스트한다.
화면 문자열을 `screen.ts`로 뺀 이유는 하나다. 바이트 한도를 테스트로 잡기 위해서다.
tiro는 이 한도로 두 번 막혔고, 두 번 모두 실기기에서야 알았다.

### 저장 데이터
`bridge.setLocalStorage`에 저장한다. 브라우저 `localStorage`는 `.ehpk` WebView 재시작 시 지워진다.

| 키 | 값 | 누가 쓰나 |
|---|---|---|
| `destinations` | 줄바꿈으로 나눈 역 이름, 최대 8개 | 사용자가 폰에서 넣는다 |
| `recentOrigins` | 줄바꿈으로 나눈 역 이름, 최대 5개 | 앱이 자동으로 기록한다 |

### 타입
```ts
type Leg = { line: string; stops: string[] }   // stops[0] 승차역, 마지막이 하차역
type Plan = { from: string; to: string; legs: Leg[] }
type Fix = { station: string; at: number }     // at = epoch ms
type Direction = 0 | 1
```

## 8. 상태 기계

```
ORIGIN ──탭──▶ DEST ──탭──▶ PICK ──탭──▶ RIDING ──▶ ARRIVED
                              ▲            │  │
             후보 1대면 건너뜀 └────────────┘  └─환승역─▶ TRANSFER ─탭─▶ PICK
```

| 상태 | 화면 | polling |
|---|---|---|
| `ORIGIN` | 가까운 역 + 최근 출발역 목록 | 없음 |
| `DEST` | 저장한 도착지 목록 | 없음 |
| `PICK` | 방향이 맞는 도착 예정 열차 목록 | 10초 (`/arrival`) |
| `RIDING` | 상자 3개 동행 화면 | 10초 (`/position`) |
| `TRANSFER` | 환승 안내 전체 화면 | 없음 |
| `ARRIVED` | 도착 화면 | 없음 |

`ORIGIN`에서 더블탭은 `shutDownPageContainer(1)`이다. 다른 화면의 더블탭은 한 단계 뒤로 간다.
`RIDING`은 `Leg` 하나를 담당한다. 마지막 `stops`에 닿으면 다음 `Leg`가 있으면 `TRANSFER`로,
없으면 `ARRIVED`로 간다.

## 9. 화면

### 9.1 출발역 (`ORIGIN`)
목록이다. GPS가 되면 가까운 순으로 최대 8개, 각 항목에 거리를 붙인다.
GPS가 실패하면 최근 출발역만 보여주고 맨 위에 `GPS 실패`를 적는다.

```
잠실  120m
잠실새내  680m
석촌  910m
[최근: 교대]
```

### 9.2 도착지 (`DEST`)
폰에 저장한 도착지 목록이다. 비어 있으면 안내 화면을 띄운다.

### 9.3 경로 계산 중
전체 화면이다. 계산된 경로를 여기서 보여준다. 탭이 필요 없다.

```
     잠실 → 경복궁

     2호선 13정거장
     ▶ 을지로3가 환승
     3호선 3정거장

     열차를 확인하는 중...
```

### 9.4 주행 중 (`RIDING`)
텍스트 컨테이너 3개. 각각 `borderWidth: 1`, `width: 576`.

| 컨테이너 | y | height | 내용 |
|---|---|---|---|
| 1 | 0 | 104 | `다음` + 다음 역 이름. 여백을 크게 준다 |
| 2 | 104 | 104 | `하차까지 N 정거장 · 약 M분` + 진행 막대 |
| 3 | 208 | 80 | 다음 행동. 환승이 없으면 종착역 |

```
┌────────────────────────────────────────┐
│                                        │
│   다음        역 삼                     │
│                                        │
├────────────────────────────────────────┤
│   하차까지    4 정거장 · 약 8분          │
│   ●━●━●━○━○━○━◉ 강남                   │
├────────────────────────────────────────┤
│   교대에서 3호선 갈아탐 (2정거장 뒤)      │
└────────────────────────────────────────┘
```

진행 막대: `●` 지나온 역(관측), `◌` 지나온 역(추정), `○` 남은 역, `◉` 하차역.
역이 12개를 넘으면 앞을 `⋯`로 줄인다.
`isEventCapture: 1`은 컨테이너 1개에만 둔다(SDK 요구).

### 9.5 하차 2정거장 전
컨테이너 1개가 화면 전체를 쓴다. 상황 하나에 화면 전부를 내주는 것이 위계다.

```
┌────────────────────────────────────────┐
│                                        │
│          다 음 다 음 에  내 립 니 다      │
│                                        │
│              강 남                      │
│                                        │
│          역삼 → 강남 · 약 4분            │
│                                        │
└────────────────────────────────────────┘
```

하차 1정거장 전에는 `다 음 에  내 립 니 다`로 바뀐다.

### 9.6 환승 (`TRANSFER`)
```
┌────────────────────────────────────────┐
│                                        │
│        교 대 에 서  갈 아 탑 니 다        │
│                                        │
│        2호선  →  3호선                  │
│        방면: 경복궁                      │
│                                        │
│        탭하면 다음 열차를 고릅니다        │
└────────────────────────────────────────┘
```

### 9.7 신호 끊김
```
┌────────────────────────────────────────┐
│   신호 끊김                             │
│   마지막 확인: 선릉 (52초 전)            │
├────────────────────────────────────────┤
│   추정      역삼 부근 · 하차까지 3 정거장  │
│   ●━●━◌━◌━○━◉                          │
│                                        │
│   탭: 열차 다시 고르기                   │
└────────────────────────────────────────┘
```

`◌`와 `●`의 차이가 추정과 관측을 가른다. 화면이 스스로 추정이라고 말한다.

## 10. 알고리즘

### 10.1 인접 그래프
간선 규칙 다섯이다.

1. 같은 `line + branch`에서 `order`가 연속인 역끼리 잇는다. 가중치 1.
2. `NNN-` 지선의 첫 역을 같은 노선의 `FR_CODE = NNN` 역에 잇는다. 가중치 1.
3. `X` 알파벳 분기의 첫 역을 같은 노선의 `FR_CODE = order - 1` 역에 잇는다. 가중치 1.
4. 순환 노선(2호선)은 본선의 마지막 역과 첫 역을 잇는다. 가중치 1.
5. 같은 이름 다른 노선끼리 잇는다(환승). 가중치 `TRANSFER_COST = 5`.

노드는 `노선|역이름`이다. 실측: 노드 799, 승차 간선 775, 환승 간선 176, 고립 노드 0.

### 10.2 경로 탐색
출발역 이름의 모든 노선 노드에서 출발해 도착역 이름의 아무 노선 노드에 닿는
다익스트라 최단경로다. 결과를 노선이 바뀌는 지점에서 잘라 `Leg[]`로 만든다.

검증(2026-09-20, 실제 데이터):

| 시험 | 결과 |
|---|---|
| 잠실 → 경복궁 | 2호선 13 ▶ 을지로3가 ▶ 3호선 3 |
| 서울역 → 강남 | 4호선 7 ▶ 사당 ▶ 2호선 4 |
| 노원 → 여의도 | 4호선 11 ▶ 동대문역사문화공원 ▶ 5호선 10 |
| 수원 → 강남 | 수인분당선 15 ▶ 정자 ▶ 신분당선 5 |
| 2호선 충정로 → 시청 | 1정거장 (순환이 닫힌다) |
| 1호선 서울역 → 수원 | 22정거장 (경부선 분기를 건넌다) |
| 5호선 광화문 → 마천 | 22정거장 (마천지선) |

**한계를 인정한다.** 이 그래프는 급행과 직결 운행 패턴을 모른다.
정거장 수 기준 최단이지 소요시간 최단이 아니다. `TRANSFER_COST`는 조정 손잡이다.

### 10.3 방향 판정
`updnLine` 필터는 반대 승강장 열차를 거르므로 중요하다.
`Leg`의 `stops` 앞쪽에서 **같은 `branch`를 공유하는 첫 인접 쌍**을 찾아 `order` 증감으로 정한다.
증가하면 1(하행/내선), 감소하면 0(상행/외선)이다.
그런 쌍이 없으면 `null`이다. 그때는 방향으로 거르지 않고 후보를 모두 보여준다.
잘못 걸러 엉뚱한 열차를 잡는 것보다, 한 번 더 묻는 편이 안전하다.

### 10.4 가까운 역
하버사인 거리로 좌표가 있는 역을 정렬한다. 같은 이름의 여러 노선은 하나로 묶는다.
`accuracy`가 1000 m를 넘으면 GPS를 버리고 최근 출발역만 보여준다.

### 10.5 탑승 열차 잡기
1. 현재 `Leg`의 방향을 10.3으로 계산한다.
2. `/arrival/{승차역}`을 부른다. 같은 노선, 같은 방향, 열차번호가 있는 것만 남긴다.
3. 후보가 1대면 바로 `RIDING`으로 간다. 2대 이상이면 목록으로 되묻는다.
4. 0대면 "도착 정보 없음 · 탭하면 다시 확인"을 띄운다.

### 10.6 추적
1. 10초마다 `/position/{노선명}`을 부른다.
2. `trainNo`가 같은 항목을 찾으면 `{역, 시각}`을 관측 기록에 넣는다.
3. 남은 정거장은 `stops`에서 현재 역과 하차역의 거리다.
4. 남은 시간은 관측 기록에서 구한 평균 역간 소요시간 × 남은 정거장이다.
   관측이 2건 미만이면 `DEFAULT_PACE_MS = 120000`을 쓴다.

### 10.7 추정 (신호 끊김)
1. `trainNo`를 못 찾으면 마지막 관측에서 흐른 시간을 관측 평균 소요시간으로 나눈다.
2. 그 수만큼 `stops`를 앞으로 민다. 이 구간은 `◌`로 그린다.
3. 마지막 관측에서 `STALE_MS = 180000`이 지나면 추정을 멈추고 "신호 끊김" 화면을 띄운다.
4. `trainNo`를 다시 찾으면 관측으로 되돌아간다.

## 11. 실패 처리

| 상황 | 동작 |
|---|---|
| GPS 실패 또는 타임아웃 | 최근 출발역만 보여준다. 맨 위에 `GPS 실패`를 적는다 |
| 최근 출발역도 없음 | "폰에서 도착지를 먼저 넣으세요" 안내. 출발역은 도착지 목록에서 고르게 한다 |
| 경로를 못 찾음 | "경로를 찾지 못했습니다 · {출발} → {도착}" + 탭 복구 |
| 워커 403 | "앱 설정이 서버와 맞지 않습니다" + 탭 복구 |
| 워커 5xx 또는 무응답 | 10.7 추정으로 버틴다. `STALE_MS` 초과 시 "신호 끊김" |
| 후보 열차 0대 | "도착 정보 없음 · 탭하면 다시 확인" |
| `trainNo`가 목록에서 사라짐 | 추정으로 버티다 "탭: 열차 다시 고르기"를 띄운다 |
| `rebuildPageContainer`가 `false` | 반환값을 확인한다. 상자 3개가 거부되면 전체 화면 1개로 떨어뜨린다 |
| 텍스트가 바이트 한도 초과 | 역 이름을 줄이지 않는다. 진행 막대를 먼저 줄인다 |

**모든 실패 화면에 탭 복구 경로를 둔다.** 예외는 없다.

## 12. 검증

### 자동 (`node --test src/*.test.ts`)
1. `stations.ts` — 노선별 역 순서, 환승역 판정, subwayId → 노선명
2. `route.ts` — 경로 탐색(직선, 순환, 지선, 분기, 환승), 방향, 남은 정거장, 속도, 추정 위치
3. `geo.ts` — 하버사인 거리, 가까운 역 정렬, 같은 이름 묶기
4. `screen.ts` — 진행 막대, 바이트 한도, 각 화면 문자열
5. `api.ts` — 두 API의 `updnLine` 정규화, 빈 응답과 오류 응답

### 실기기
1. 상자 3개 레이아웃이 팔 뻗은 거리에서 읽히는가
2. 각 화면이 바이트 한도 안에 드는가 (`rebuild` 반환값 로그)
3. `getAppLocation`이 실제로 값을 주는가. `accuracy`가 몇 미터인가
4. 코레일 직결 구간(1호선 또는 4호선)에서 `trainNo`가 유지되는가
5. 지하 구간에서 10초 polling이 얼마나 자주 실패하는가

개발 중 로그는 tiro와 같다. `navigator.sendBeacon('/__log', msg)`와 Vite 미들웨어로
dev server 터미널에 찍는다. `import.meta.env.DEV`일 때만 보낸다.

## 14. 미해결

1. **두 소스의 이름 표기가 다르다.** 역 목록은 "서울역", "경의선"이라 하고
   실시간 API는 "서울", "경의중앙선"이라 한다(도착 API 실측).
   실시간 키를 받는 즉시 두 소스를 맞대어 별칭 표를 만든다. 추측으로 채우지 않는다.
2. 2호선 내선/외선이 `updnLine`의 0과 1 중 어느 쪽인지. 실시간 응답으로 확인한다.
3. 서울 API의 rate limit 수치. `poll failed`가 잦으면 polling을 15초로 늘린다.
4. 코레일 직결 구간의 `trainNo` 연속성. 끊기면 그때 자동 재탐색을 넣는다.
5. `.ehpk` 페이지의 scheme. 워커가 https이므로 막힐 이유가 없지만 배포 때 확인한다.
6. 이미 탑승한 상태로 앱을 여는 경우. 1차는 승강장에서 시작하는 것만 지원한다.
