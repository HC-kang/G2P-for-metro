## 2026-09-20 목표와 기준 (사용자 확인)

- 핵심 장면은 "탑승 중 동행"이다. 열차를 탄 뒤가 주전장이다. 남은 정거장, 환승 시점, 하차 시점을 안내한다.
- 입력 방식은 "폰에 경로 저장 → G2에서 선택"이다. 경로 탐색은 1차 범위 밖이다.
- 기존 앱의 불만 4가지를 모두 받았다: 조작이 번거롭다, 정보가 정적이다, 하차/환승을 못 챙긴다, 화면이 지저분하다.
- 사용자 원문: "텍스트로만 이루어져있는데, 단순 줄바꿈으로만 구분되어있어서 정보의 위계도 없고, '그냥 정보 나열해놨으니 니가 봐라'라는듯한 태도가 마음에 들지 않아"
- 따라서 합격 기준은 두 가지다. (1) 화면에 정보 위계가 있다. (2) 앱이 "지금 알아야 할 한 가지"를 먼저 말한다.

## 2026-09-20 서울 지하철 API 실측 (curl)

### 실시간 열차 위치 — `swopenapi.seoul.go.kr`
- `GET http://swopenapi.seoul.go.kr/api/subway/{KEY}/json/realtimePosition/0/{N}/{노선명}`
- 200 정상. `Access-Control-Allow-Origin: *`. preflight(OPTIONS)도 200이다. → WebView에서 직접 호출한다. 프록시가 필요 없다.
- **HTTPS는 응답하지 않는다(타임아웃).** http 전용이다. 이것이 최대 위험이다. 아래 "미검증" 참고.
- 응답 필드: `trainNo`(열차번호), `statnNm`(현재 역), `updnLine`(0=상행/외선, 1=하행/내선), `trainSttus`(0=진입, 1=도착, 2=출발), `statnTnm`(종착역), `directAt`(급행), `recptnDt`(초 단위 시각).
- 실측: 열차 `2301`이 약 1분 사이에 잠실새내 → 잠실로 이동했다. **`trainNo`로 특정 열차를 계속 추적할 수 있다.**
- 노선 커버리지 확인: 2호선 37대, 9호선 26대, 신분당선 12대, 수인분당선 32대, 경의중앙선 23대. 코레일·민자 노선도 나온다.

### 실시간 도착 정보 — 같은 도메인
- `GET .../json/realtimeStationArrival/0/{N}/{역명}`
- `btrainNo`(도착 예정 열차번호), `barvlDt`(도착까지 남은 초), `arvlMsg2`(예: "서울 출발"), `trainLineNm`(예: "광운대행 - 시청방면"), `btrainSttus`(일반/급행)를 준다.
- 용도: 승강장에서 탑승할 열차의 `trainNo`를 미리 잡는다.

### 역 목록 — `openapi.seoul.go.kr:8088`
- `GET http://openapi.seoul.go.kr:8088/{KEY}/json/SearchSTNBySubwayLineInfo/1/800/`
- 799개 역. 필드 `STATION_CD`, `STATION_NM`, `LINE_NUM`("01호선"), `FR_CODE`("P148", "151").
- `FR_CODE`의 숫자 부분이 노선 내 역 순서다. 환승역은 같은 `STATION_NM`이 여러 `LINE_NUM`에 나온다.
- CORS `*`. 역시 http 전용이다.
- **빌드 시점에 한 번 받아 정적 JSON으로 번들한다.** 런타임 의존을 만들지 않는다.

## 2026-09-20 미검증 (착수 전 확인 필요)

1. **`.ehpk` private build의 페이지 scheme.** 페이지가 https면 http API 호출이 mixed content로 차단된다. QR sideload(`http://<ip>:5173`)는 http라서 문제가 없다. 1차는 sideload로 만들고, 배포 시점에 https 프록시 필요 여부를 판단한다.
2. **G2 폰트 크기는 조절할 수 없다**(tiro 확인). 큰 글씨로 위계를 만들 수 없다. 여백, 정렬, 컨테이너 분할, 문자 그래픽으로 만들어야 한다. 이미지 컨테이너(288x144, 페이지당 4개) 렌더링은 마지막 수단이다.
3. 코레일 직결 구간(1·3·4호선, 경의중앙선 등)에서 `trainNo`가 중간에 바뀌는지 확인이 필요하다.
4. 지하 구간에서 폰 네트워크가 끊기는 빈도. polling 실패 시 동작을 정해야 한다.

- `FR_CODE`의 숫자만 뽑으면 안 된다. `P142`(가산디지털단지)와 `142`(구일)가 충돌한다. 1호선 20건, 5호선 7건, 경의선 2건이 겹쳤다.

- **순서 산술 대신 인접 그래프 BFS를 쓴다.** 간선 규칙 4개로 순환선·지선·분기가 한 번에 풀린다. 노드 799, 간선 775, 고립 0.

## 2026-09-20 실시간 키 실측: updnLine을 쓰지 말 것

- **두 API의 `updnLine` 표기가 다르고, 노선마다 극성이 반대다.** 같은 열차번호로 교차 검증했다.
  `상행 → 0`(34건), `하행 → 1`(31건), `외선 → 1`(14건), `내선 → 0`(14건). 4%는 어느 쪽에도 안 맞았다(회차 열차 추정).
- `order` 증가가 어느 방향인지도 노선마다 다르다. 1·3·4·5·6·7·8호선, 신분당선, 수인분당선은 `order` 증가 = 하행(1)이다. **2호선은 `order` 증가 = 내선(0), 9호선은 `order` 증가 = 상행(0)으로 반대다.**
- **해법: `updnLine`을 읽지 않는다.** `trainLineNm`의 `"…방면"` 역이 경로의 다음 역(`stops[1]`)과 같은지로 방향을 가른다. 극성 표가 통째로 필요 없어졌다. `direction()` 함수와 `updn` 필드를 지웠다.
- 근거: `"…방면"`은 급행이든 일반이든 **물리적으로 인접한 다음 역**이다. 9호선 급행 `9641`이 여의도에서 `국회의사당방면`, 노량진에서 `샛강방면`으로 나왔다. 둘 다 인접역이다.
- `trainLineNm` 형식은 `"{종착역}행 - {다음역}방면"`이고 급행이면 `" (급행)"`이 붙는다. 201건 전부 이 꼴이었다.
- 파싱 주의: `$` 앵커를 쓰면 `(급행)` 꼬리에서 실패한다. 괄호 별칭(`총신대입구(이수)방면`)도 떼야 역 목록과 맞는다. 둘을 처리하면 201건 중 201건 파싱, 199건이 역 목록과 일치한다.
- 실측 필터 결과: 2호선 강남 교대방면 4대 중 2대, 1호선 시청 종각방면 8대 중 4대. 정확히 절반으로 갈린다.

## 2026-09-20 실수와 원인: HMR이 polling 루프를 쌓았다

- 증상: "7283번 열차를 찾지 못했습니다"가 반복해서 떴다. 로그에 `poll failed` 2,335회, `train not in feed` 512회가 찍혔다. `show`가 10초 주기보다 훨씬 잦았다.
- 원인: Vite HMR은 모듈을 다시 실행한다. `main.ts`가 `setTimeout` 루프와 `onEvenHubEvent` 구독을 정리하지 않아, 편집할 때마다 인스턴스가 하나씩 쌓였다. 옛 인스턴스는 `trip`이 `null`이라 `leg()`에서 예외가 났고 그것이 `poll failed`로 찍혔다. 살아남은 루프들이 같은 화면을 서로 덮어썼다.
- 확인: 7283은 위치 API에 실제로 있었다(도봉산). 노원 도착 예정 4건 중 위치 API에 없는 것은 0건이었다. 워커도 12/12 정상(0.47초)이었다. 즉 API 문제가 아니었다.
- 수정 3가지:
  1. `import.meta.hot.dispose`에서 `stopPolling()`과 `unsubscribe()`를 부른다.
  2. polling에 세대 번호를 둔다. `stopPolling()`이 세대를 올리고, 옛 루프는 자기 세대가 아니면 아무것도 하지 않는다. `await` 뒤에도 세대를 다시 확인한다.
  3. 한 번 놓친 것으로 오류를 띄우지 않는다. 3회 연속(30초) 실패해야 오류 화면을 낸다.
- 교훈: 실기기 디버깅에서 HMR은 상태를 가진 코드의 증상을 통째로 왜곡한다. 타이머와 구독을 쓰면 `dispose`를 먼저 붙인다.

## 2026-09-20 G2 화면 폭

- **전각 문자를 세지 않으면 화면이 조용히 접힌다.** `─` 34개는 68칸이다. 진행 띠의 `━` 구분자도 12개를 이으면 46칸이다.
- `cols()`로 칸을 센다(한글·도형 2칸, 그 밖 1칸). `MAX_COLS = 32`는 아직 추측값이다. 실측 범위는 "32칸은 안전, 68칸은 넘침"이다.
- 긴 역 이름(`동대문역사문화공원` 18칸)은 자간을 벌리면 넘친다. `hero()`가 넘치면 자간을 포기한다. `pair()`가 넘치면 줄을 나눈다.
- 머리줄은 `현재시각 HH:MM`이다. 화면에 도착 예정 시각도 나오므로 현재 시각임을 밝혀야 한다(사용자 지적).

- 시뮬레이터 폰트는 화면 폭의 절반만 쓴다. 폭 한도는 시뮬레이터로 정하지 않는다. 줄 수는 신뢰한다(README: 레이아웃 검증에 충분).
- 관측이 새 역으로 바뀔 때 `fix 역 상태 left N pace Ns`를 남긴다. 전엔 주행 중 로그가 `req`뿐이라 위치를 알 수 없었다.

## 2026-09-24 GPS 모사로 현위치 갱신 검증 (사용자 요청)

- 도구: dev 서버 `/__gps`가 `.dev/gps.json`(`{lat, lon, acc?, ts?}`)을 그대로 돌려준다. 앱은 개발 모드 `?gps=dev`일 때만 브리지 대신 이 피드를 읽고, "새 측위 기다리기"도 이 피드를 0.5초마다 다시 본다. **파일을 고치면 폰이 움직인 것이고, `ts`를 묵히면 묵은 위치를 모사한다.** 배포본은 이 코드를 타지 않는다. `.dev/`는 gitignore.
- 시나리오(하계→공릉→태릉입구→먹골)와 결과:
  - 공릉, 신선 → `age 0` → 목록 즉시 갱신(공릉 1순위).
  - 태릉입구, 5분 묵음 → `age 300` → 기다림 → 3초 뒤 신선한 값 → `gps fresh yes` → 태릉입구 1순위, 배너 없음.
  - 먹골, 10분 묵음, 새 값 없음 → `age 600` → 8초 대기 → `gps fresh no` → 후보 12개 + `위치가 오래됐습니다 · 직접 고르세요` 배너.
  - 콘솔 오류 0.
- 결론: **앱 쪽 갱신 로직은 맞다.** 폰에서 "처음 한 번만 잡히는" 현상은 호스트가 묵은 위치를 주는 문제이고, 이제 `timestamp`로 걸러 새 측위를 요청한다. 실기기의 `timestamp` 단위와 `onAppLocationChanged`가 실제로 오는지는 여전히 폰 로그(`gps … ts N age N`, `gps push …`)로 확인해야 한다.
- 검증 방법 메모: 출발역 화면에서 더블탭은 종료라, 도착지 화면으로 한 번 들어갔다가 더블탭해야 `showOrigin()`이 다시 돈다.
