# 제약 — 플랫폼·API·데이터에서 실측한 사실

[context.md](context.md)에서 옮겨 왔다. 날짜순이다. 새 항목은 맨 아래에 붙인다.

## 2026-09-20 서울 지하철 API 실측 (curl)

### 실시간 열차 위치 — `swopenapi.seoul.go.kr`
- `GET http://swopenapi.seoul.go.kr/api/subway/{KEY}/json/realtimePosition/0/{N}/{노선명}`
- 200 정상. `Access-Control-Allow-Origin: *`. preflight(OPTIONS)도 200이다. → WebView에서 직접 호출한다. 프록시가 필요 없다.
- **HTTPS는 응답하지 않는다(타임아웃).** http 전용이다. 이것이 최대 위험이다. 아래 "미검증" 참고.
- 응답 필드: `trainNo`(열차번호), `statnNm`(현재 역), `updnLine`(0=상행/외선, 1=하행/내선), `trainSttus`(0=진입, 1=도착, 2=출발), `statnTnm`(종착역), `directAt`(급행), `recptnDt`(초 단위 시각).
- 실측: 열차 `2301`이 약 1분 사이에 잠실새내 → 잠실로 이동했다. **`trainNo`로 특정 열차를 계속 추적할 수 있다.**
- 노선 커버리지 확인: 2호선 37대, 9호선 26대, 신분당선 12대, 수인분당선 32대, 경의중앙선 23대. 코레일·민자 노선도 나온다.

### 실시간 도착 정보 — 같은 도메인
- `GET .../json/realtimeStationArrival/0/{N}/{역명}`
- `btrainNo`(도착 예정 열차번호), `barvlDt`(도착까지 남은 초), `arvlMsg2`(예: "서울 출발"), `trainLineNm`(예: "광운대행 - 시청방면"), `btrainSttus`(일반/급행)를 준다.
- 용도: 승강장에서 탑승할 열차의 `trainNo`를 미리 잡는다.

### 역 목록 — `openapi.seoul.go.kr:8088`
- `GET http://openapi.seoul.go.kr:8088/{KEY}/json/SearchSTNBySubwayLineInfo/1/800/`
- 799개 역. 필드 `STATION_CD`, `STATION_NM`, `LINE_NUM`("01호선"), `FR_CODE`("P148", "151").
- `FR_CODE`의 숫자 부분이 노선 내 역 순서다. 환승역은 같은 `STATION_NM`이 여러 `LINE_NUM`에 나온다.
- CORS `*`. 역시 http 전용이다.
- **빌드 시점에 한 번 받아 정적 JSON으로 번들한다.** 런타임 의존을 만들지 않는다.
- `SearchSTNTimeByFRCodeService`(역간 소요시간)는 `ERROR-500`이다. 쓸 수 없다.

### API key
- `sample` key는 5건만 준다. 100건 요청은 `ERROR-336`으로 거부된다(오류 문구는 건수 한도를 말하지만 실제 원인은 sample 제한이다).
- 실제 key는 data.seoul.go.kr에서 무료로 발급한다. tiro와 같은 BYOK로 간다.

## 2026-09-20 미검증 (착수 전 확인 필요)

1. **`.ehpk` private build의 페이지 scheme.** 페이지가 https면 http API 호출이 mixed content로 차단된다. QR sideload(`http://<ip>:5173`)는 http라서 문제가 없다. 1차는 sideload로 만들고, 배포 시점에 https 프록시 필요 여부를 판단한다.
2. **G2 폰트 크기는 조절할 수 없다**(tiro 확인). 큰 글씨로 위계를 만들 수 없다. 여백, 정렬, 컨테이너 분할, 문자 그래픽으로 만들어야 한다. 이미지 컨테이너(288x144, 페이지당 4개) 렌더링은 마지막 수단이다.
3. 코레일 직결 구간(1·3·4호선, 경의중앙선 등)에서 `trainNo`가 중간에 바뀌는지 확인이 필요하다.
4. 지하 구간에서 폰 네트워크가 끊기는 빈도. polling 실패 시 동작을 정해야 한다.

## 2026-09-20 API key 조사

- `sample` 키의 한도는 `openapi.seoul.go.kr:8088`에서 **1~5번 항목 고정**이다. 오프셋을 옮겨도 `ERROR-335`다. 그래서 `stations.json`을 만들려면 실제 키가 필요하다. `swopenapi` 쪽 `sample` 한도도 5건이다.
- 데이터셋 이름 주의: "서울시 지하철역 정보"라는 이름은 열린데이터광장 목록에 없다. 서비스 이름 `SearchSTNBySubwayLineInfo`는 실재하고 799개역을 준다.
- "지하철역 최단경로이동정보 현황"은 역 구내 이동/환승 통로 정보다. 노선 내 역 순서가 아니다. 1차 범위에는 쓰지 않는다. 나중에 "빠른 환승 칸" 기능의 후보다.
- 미검증: 열린데이터광장 인증키 하나가 `openapi.seoul.go.kr:8088`과 `swopenapi.seoul.go.kr` 양쪽에 모두 통하는지. 키를 받는 즉시 두 도메인을 함께 시험한다.
- 대안: 8088이 거부하면 열린데이터광장의 CSV 파일 내려받기(`FILE` 표시 데이터셋)로 역 목록을 얻는다.

- 일반 키로 `SearchSTNBySubwayLineInfo` 799개역 전량을 받았다.

## 2026-09-20 좌표 데이터와 GPS 지원 확인

- `GET http://openapi.seoul.go.kr:8088/{KEY}/json/subwayStationMaster/1/1000/`가 `BLDN_NM`, `ROUTE`, `LAT`, `LOT`를 준다. 784개역이다.
- 역 목록의 고유 역 이름 655개 중 647개가 매칭된다. 안 되는 8개는 최근 개통역이다(운정중앙, 평택지제, 시우 등). 직접 고르기로 넘긴다.
- **G2 SDK가 위치를 정식 지원한다.** `bridge.getAppLocation()`, `startAppLocationUpdates()`, `stopAppLocationUpdates()`, `onAppLocationChanged()`. 값은 `{latitude, longitude, accuracy, altitude, speed, heading, timestamp}`이고 `AppLocationAccuracy`는 low/medium/high다.
- `app.json`이 허용하는 권한 전체(CLI 스키마 실측): `g2-microphone`, `phone-microphone`, `album`, `location`, `network`, `camera`.

## 2026-09-20 실시간 키 실측: updnLine을 쓰지 말 것

- **두 API의 `updnLine` 표기가 다르고, 노선마다 극성이 반대다.** 같은 열차번호로 교차 검증했다.
  `상행 → 0`(34건), `하행 → 1`(31건), `외선 → 1`(14건), `내선 → 0`(14건). 4%는 어느 쪽에도 안 맞았다(회차 열차 추정).
- `order` 증가가 어느 방향인지도 노선마다 다르다. 1·3·4·5·6·7·8호선, 신분당선, 수인분당선은 `order` 증가 = 하행(1)이다. **2호선은 `order` 증가 = 내선(0), 9호선은 `order` 증가 = 상행(0)으로 반대다.**
- **해법: `updnLine`을 읽지 않는다.** `trainLineNm`의 `"…방면"` 역이 경로의 다음 역(`stops[1]`)과 같은지로 방향을 가른다. 극성 표가 통째로 필요 없어졌다. `direction()` 함수와 `updn` 필드를 지웠다.
- 근거: `"…방면"`은 급행이든 일반이든 **물리적으로 인접한 다음 역**이다. 9호선 급행 `9641`이 여의도에서 `국회의사당방면`, 노량진에서 `샛강방면`으로 나왔다. 둘 다 인접역이다.
- `trainLineNm` 형식은 `"{종착역}행 - {다음역}방면"`이고 급행이면 `" (급행)"`이 붙는다. 201건 전부 이 꼴이었다.
- 파싱 주의: `$` 앵커를 쓰면 `(급행)` 꼬리에서 실패한다. 괄호 별칭(`총신대입구(이수)방면`)도 떼야 역 목록과 맞는다. 둘을 처리하면 201건 중 201건 파싱, 199건이 역 목록과 일치한다.
- 실측 필터 결과: 2호선 강남 교대방면 4대 중 2대, 1호선 시청 종각방면 8대 중 4대. 정확히 절반으로 갈린다.

## 2026-09-20 노선명 별칭과 실시간 미지원 노선

- 역 목록과 실시간 API의 노선명이 다르다. 실시간 API에 후보 이름을 직접 던져 확인했다. 추측하지 않았다.
  - `경의선` → `경의중앙선` (id 1063)
  - `우이신설경전철` → `우이신설선` (id 1092)
- **실시간 API가 지원하지 않는 노선 5개**: 김포도시철도, 용인경전철, 의정부경전철, 인천선, 인천2호선. 역 100개다. 서울시 TOPIS 데이터라 인천·김포·용인·의정부 자체 노선이 없다.
- 이 노선들을 그래프에서 뺀다. 남겨 두면 경로가 추적 불가 구간을 지나고 안내가 조용히 멈춘다.
- 노선 ID 19개를 받았다. 역 699/799개가 추적 가능하다.
- 빌드 스크립트가 주요 노선(1~9호선) ID가 빠지면 멈춘다. 막차 뒤에 돌리면 `lines`가 비어 버리기 때문이다.

## 2026-09-20 G2 화면 폭

- **전각 문자를 세지 않으면 화면이 조용히 접힌다.** `─` 34개는 68칸이다. 진행 띠의 `━` 구분자도 12개를 이으면 46칸이다.
- `cols()`로 칸을 센다(한글·도형 2칸, 그 밖 1칸). `MAX_COLS = 32`는 아직 추측값이다. 실측 범위는 "32칸은 안전, 68칸은 넘침"이다.
- 긴 역 이름(`동대문역사문화공원` 18칸)은 자간을 벌리면 넘친다. `hero()`가 넘치면 자간을 포기한다. `pair()`가 넘치면 줄을 나눈다.
- 머리줄은 `현재시각 HH:MM`이다. 화면에 도착 예정 시각도 나오므로 현재 시각임을 밝혀야 한다(사용자 지적).

## 2026-09-21 역 이름 표기가 API마다 다르다 (중대)

- **도착 API는 자기 표기로만 역을 받는다.** `/arrival/공릉`은 `INFO-200 해당하는 데이터가 없습니다`, `/arrival/공릉(서울산업대입구)`는 정상이다.
- 표기가 세 갈래다. 괄호 붙은 역 67개를 실제로 두드려 확인했다.
  - 짧은 이름으로 되는 역 38개
  - 괄호 이름이 필요한 역 20개 (`총신대입구(이수)`, `군자(능동)`, `몽촌토성(평화의문)` 등)
  - 제3의 별칭을 쓰는 역 9개. `공릉`은 역 목록도 좌표 데이터도 `공릉(서울과학기술대)`라 하는데 도착 API는 `공릉(서울산업대입구)`다. **좌표 데이터(subwayStationMaster)를 별칭 출처로 쓰면 안 된다.**
- **위치 API는 또 다르다.** `realtimePosition`의 `statnNm`이 `군자(능동)`처럼 괄호를 달고 온다. 역 목록은 `군자`다. 비교할 때 괄호를 떼지 않으면 그 역에서 관측이 끊겨 현위치가 고정된다.
- 해결:
  1. 빌드 때 도착 API를 훑어 `arrivalNames` 표를 만든다. 정식 표기는 이웃 역 응답의 `trainLineNm`의 `…방면`에서 줍는다. 550/566개를 확인했고 별칭 20개를 찾았다.
  2. 런타임 비교는 `bare()`로 양쪽 괄호를 떼고 한다.
  3. 표는 **병합**한다. 막차 뒤에 돌리면 도착 열차가 없어 대부분 실패하는데, 그때 표를 잃으면 안 된다. 실행할 때마다 아는 것이 늘기만 한다.
- 주의: 이 훑기는 "이름이 틀림"과 "지금 열차가 없음"을 구별하지 못한다. 반드시 운행 시간대에 돌린다.

## 2026-09-21 서울 실시간 API는 하루 1000건이 한도다 (중대)

- `ERROR-337 데이터요청은 일일 호출건수 최대 1000건을 넘을 수 없습니다.`
- **오류도 HTTP 200에 본문으로 온다.** 목록이 없다고 빈 배열로 넘기면 "도착 정보가 없습니다"로 둔갑해 원인을 숨긴다. `ApiError`로 던지고 화면에 그대로 말한다.
- `INFO-200`은 오류가 아니다. "그 역에 올 열차가 지금 없다"는 뜻이다(막차 뒤에 흔하다).
- 10초 고정 폴링은 시간당 360건이다. 두 번만 타면 바닥난다. 빌드 훑기도 566건을 태웠다.
- 해결: 상황별 폴링. 하차 2정거장 이내 15초, 열차 대기 20초, 그 밖 35초. 워커 캐시 20초.
  실측 예산: 21정거장 왕복 2회에 194건(이전 방식이었다면 600건).
- 빌드 스크립트는 이미 아는 것을 **병합**한다. 한도를 쓴 날에는 조회가 전부 실패하므로 덮어쓰면 표를 잃는다.

## 2026-09-21 그래프의 가짜 환승과 끊긴 지선

- **이름만 같고 환승이 안 되는 역이 있다.** `subwayStationMaster`가 노선별 좌표를 주므로 같은 이름의 최대 거리로 가려낸다. 600m를 경계로 쓴다.
  - 별개 역: 양평 53.5km(중앙선/5호선), 운정 3.6km(경의중앙선/GTX-A), 신촌 715m(2호선/경의중앙선)
  - 진짜 환승: 서울역 510m, 잠실 401m, 동대문역사문화공원 343m, 청량리 339m, 신당 311m
  - 빌드 때 계산해 `noTransfer`로 저장한다. 손으로 적지 않는다.
- 미해결: 경의중앙선 서울역 지선(P312 신촌, P313 서울역)이 본선과 끊겨 있다. 실제로는 가좌에서 분기하는데 `FR_CODE`에 숫자 규칙이 없다(P312 ↔ K315). 지선 운행이 하루 몇 편뿐이라 틀린 간선을 만드는 것보다 끊어 두는 편이 낫다고 보았다. 서울역은 다른 노선으로 도달한다.

## 2026-09-23 현위치가 처음 한 번만 잡히는 문제 — 호스트가 마지막 위치를 재사용한다

- 사용자 지적: "현위치 판단을 처음 한 번만 하고 그 뒤로는 안 한다. GPS인데 캐싱일 리 없다."
- 로그 증거: 한 세션의 성공한 `getAppLocation` 10번이 **소수점 5자리까지 같은 좌표**(37.63501, 127.06453)였고 정확도만 6.7~20.3m로 달랐다. 그 세션에 하계→홍대입구 주행 계획이 있었다. 앱은 `showOrigin()`마다 다시 부르므로 캐싱은 앱이 아니라 **SDK/호스트가 마지막 위치를 그대로 돌려주는 것**이다.
- SDK 단서: `AppLocation.timestamp?`, `startAppLocationUpdates({accuracy, timeoutMs, distanceFilter, intervalMs})`, `onAppLocationChanged(cb)`. (문서는 중국어, 단위 명시 없음.)
- 수정: `timestamp`가 30초보다 오래되면 묵은 것으로 보고, 갱신을 켜 **요청 시각 이후에 찍힌** 좌표를 최대 8초 기다린 뒤 끈다. 안 오면 묵은 좌표를 쓰되 목록 맨 위에 `위치가 오래됐습니다 · 직접 고르세요`를 띄운다.
- **미확인**: `timestamp` 단위. 1e12 미만이면 초로 보고 ms로 바꾼다. `gps … ts N age N` 로그의 원값으로 다음에 확정한다. timestamp가 아예 없으면 갱신으로 밀어준 첫 좌표를 새 측위로 본다.
- 주의: 사용자가 실제로 정지해 있었다면 같은 좌표가 정상이다. 이 로그만으로 100% 단정은 못 하지만, 사용자 관찰(이동 후에도 갱신 안 됨)과 mm 단위 일치가 같은 방향을 가리킨다.

## 2026-09-24 — 0.3.3: 안경 폰트 글리프 실측(사용자 보고)
- '글리프 시험' 결과. **있음:** `▁▂▃▄▅▆▇█` `● ○ ◌ ◎` `◐ ◑` `━ ─` `← → ↑ ↓` `▶ ▷` `★ ☆ ♥`. **없음:** 점자 전부(⠋⠙…), `◓ ◒ ◉`, `░ ▒ ▓`, `⇢ ➜`, `✓ ✗ ⏳ ⌛ ⚠`. 없는 글리프는 빈칸 없이 조용히 빠진다.

- 예전 스피너 ◐◓◑◒가 "얼탱이 없어" 보인 이유: 4프레임 중 ◓◒ 2개가 빠져 두 모양만 번갈아 튀었다.

- 새 글리프를 쓰기 전에는 글리프 시험 버튼으로 실기기에서 먼저 확인한다. 시뮬레이터 웹폰트는 기준이 못 된다.

## 2026-09-26 SDK 그림자 타이머가 한 번짜리 타이머를 두 번 부른다 (중대)
- even_hub_sdk 0.0.15는 `setTimeout`/`setInterval`을 가로챈다. 타이머마다 진짜 타이머와 "그림자" 항목(`remaining`, `skipNextShadowTick`)을 함께 만든다. 폰이 잠기거나 앱이 뒤로 가면 호스트가 그림자 틱을 보내 `remaining`을 깎고 콜백을 부른다. 시뮬레이터 콘솔의 `[ShadowTimers] ... queued`가 그 흔적이다.
- 한 번짜리 타이머: 그림자 틱이 콜백을 부르고 맵에서 지우지만 `cleared`를 세우지 않는다. 진짜 타이머가 나중에 깨어나면 `cleared || fn()`으로 **한 번 더 부른다.** 반복 타이머에는 `skipNextShadowTick`이 있어 덜하다.
- 결과: 폴링이 다음 폴링을 예약하는 구조라 주기마다 사슬이 두 배가 된다. 실측 2→4→8(09-24 16:35~16:36), 09-25에는 분당 폴링 476번.
- 대응: 앱의 모든 타이머 콜백을 한 번만 실행되게 감싼다. 반복 타이머는 마지막 실행 시각으로 중복을 거른다. SDK를 올릴 때 이 동작이 고쳐졌는지 다시 본다.

## 2026-09-26 SDK 그림자 타이머 동작 (난독화 해제로 확인)
- SDK는 `window.__tickShadowTimers(경과ms)`를 전역에 단다. 호스트가 이것을 불러 그림자 타이머를 돌린다. 틱마다 `shadow-timer:tick` CustomEvent(`{elapsedMs, queueSize, fired, skipped}`)를 낸다.
- 한 번짜리: 진짜 타이머는 `cleared || fn(); 맵에서 삭제`. 그림자 틱은 `remaining -= 경과; ≤0이면 fn(); 맵에서 삭제`하지만 `cleared`를 세우지 않는다. 그림자가 먼저 부르면 진짜 타이머가 나중에 또 부른다.
- 반복: 진짜 타이머가 불리면 `skipNextShadowTick`을 세워 다음 그림자 틱 한 번을 건너뛴다. 그래도 겹칠 수 있다.
- 틱이 앞 화면에서도 오는지는 미확인이다. 실기기 로그의 '1초 안에 따라오는 두 번째 폴링'은 앞 화면 틱과 맞는다(틱마다 1000ms를 깎으면 20초 타이머는 그림자가 최대 1초 먼저 부른다). 0.4.2부터 1분마다 `shadow ticks N fired M visible …`을 남긴다.
- 시뮬레이터는 그림자 틱을 보내지 않는다. 자동화 API에는 앞/뒤 전환도 없다(`/api/ping|screenshot/glasses|screenshot/webview|console|input`).
