## 2026-09-20 목표와 기준 (사용자 확인)

- 핵심 장면은 "탑승 중 동행"이다. 열차를 탄 뒤가 주전장이다. 남은 정거장, 환승 시점, 하차 시점을 안내한다.
- 입력 방식은 "폰에 경로 저장 → G2에서 선택"이다. 경로 탐색은 1차 범위 밖이다.
- 기존 앱의 불만 4가지를 모두 받았다: 조작이 번거롭다, 정보가 정적이다, 하차/환승을 못 챙긴다, 화면이 지저분하다.
- 사용자 원문: "텍스트로만 이루어져있는데, 단순 줄바꿈으로만 구분되어있어서 정보의 위계도 없고, '그냥 정보 나열해놨으니 니가 봐라'라는듯한 태도가 마음에 들지 않아"
- 따라서 합격 기준은 두 가지다. (1) 화면에 정보 위계가 있다. (2) 앱이 "지금 알아야 할 한 가지"를 먼저 말한다.

## 2026-09-21 사용자 지적 3가지

- "공릉 찍었는데 도착 예정인 지하철이 없다" → 위 별칭 문제였다.
- "태릉입구에 왔는데 현위치가 하계로 나온다" → 괄호 표기 불일치로 관측이 끊긴 것으로 본다. `bare()` 비교로 고쳤다.
- "언제 폴링되는지 표시가 필요하다" → 화면에 `노원 출발  8초 전`처럼 데이터 나이를 보여준다. 기준은 `recptnDt`(API 보고 시각)이므로 API 지연까지 포함한다.
- 열차 목록이 행선지만 보여줬다. 승강장에서 확인할 것은 **방면**이므로 `3분  공릉방면  석남행`으로 바꿨다.

## 2026-09-21 출발 노선 선택

- 사용자 지적: "최단 환승 정보라지만 호선을 지맘대로 고르면 어떡하냐."
- `planVia(from, to, line)`를 추가했다. 출발역에서 곧장 환승하는 것을 막으려고 **그 노선의 이웃 역에서 다익스트라를 시작**한다. 출발역 노드에서 시작하면 바로 환승해 다른 노선 경로가 나온다.
- 한 정거장 나갔다 되돌아오는 경로는 버린다(`legs[0].stops.at(-1) === from`).
- 선택지가 하나뿐이면 화면을 띄우지 않는다. 탭이 늘지 않는다.

## 2026-09-21 같은 유형 훑기 (사용자 요청)

사용자가 하루 동안 지적한 것을 유형으로 정리하고 같은 유형을 코드 전체에서 찾았다.

| 유형 | 처음 지적 | 같은 유형으로 더 찾은 것 |
|---|---|---|
| 재보지 않고 정한 상수 | `─` 34개(68칸), 도착지 8개 한도 | 10초 폴링이 하루 한도 1000건을 넘김 |
| 오류를 삼켜 엉뚱한 메시지 | `ERROR-337` → "도착 정보 없음" | 목록 항목을 글자 중간에서 자름(`온수행 급행` → `온수행 급`) |
| 화면에 꼭 필요한 것이 없음 | 현재 역, 현재시각, 갱신 시각 | 환승 화면의 방면이 종착역이라 승강장 표지와 기준이 다름 |
| 데이터를 조용히 버림 | GPS 오차 1km 초과, 괄호 역 이름 | 경로가 없는 도착지를 목록에서 숨김 |
| 사용자가 정할 것을 내가 정함 | 출발 호선 | (없음) |

고친 것:
- `tiers()`로 목록 곁가지를 단계적으로 줄인다. 자르지 않는다.
- 경로가 없는 도착지도 목록에 두고 `경로 없음`이라고 적는다. 숨기면 저장이 안 된 줄 안다.
- 환승 화면의 방면을 환승 뒤 **다음 역**으로 바꿨다. 승강장 표지와 같은 기준이다.
- 조회량을 직접 세어 800건을 넘으면 출발 화면과 경로 화면에 보여준다. 날짜가 바뀌면 0이 된다.
- `toMs`가 서버 시각과 10분 넘게 어긋나면 파싱을 믿지 않고 받은 시각을 쓴다. 기기 시간대가 KST가 아니면 "3시간 전" 같은 거짓말이 나온다.
- 문구를 고쳤다. `선릉 이후 190초` → `마지막 관측  선릉  3분 전`.

남긴 추측값(근거를 못 잰 것, 주석에 명시):
- `MAX_COLS = 32` — 실측 범위는 "32칸 안전, 68칸 넘침"이다. 그 사이를 못 쟀다.
- `DEFAULT_PACE_MS = 120000` — 관측 2건 미만일 때만 쓴다.
- `TRANSFER_MIN = 4` — 경로 순위에 영향을 준다. 화면에는 '약'을 붙인다.

## 2026-09-22 선택지의 단위는 노선이 아니라 (노선, 방면)이다

- 사용자 지적: "하계에서 홍대입구 갈 때 공릉방향 선택지는 없이 중계행만 나온다."
- 원인: `planVia(from, to, line)`이 노선만 지정했다. 하계에는 7호선뿐이라 양방향이 한 후보로 뭉개졌고 빠른 쪽(중계 방면)만 남았다.
- 수정: `planHop(from, to, line, next)`로 **첫 한 정거장을 지정**한다. `departures(from)`이 출발역의 모든 (노선, 방면)을 준다.
- 함정: 방향만 강제하면 다익스트라가 **출발역으로 되돌아가는 길**을 고른다. 하계에서 공릉 방면을 고르면 "공릉 → 하계 → 중계 → 노원 → 4호선"이 더 짧다고 본다. 사후에 버리면 그 방향의 진짜 경로까지 함께 잃는다. → **탐색 단계에서 출발역의 모든 노드를 막는다**(`search`의 `banned`).
- 결과: 하계→홍대입구가 중계방면 46분(4호선 경유), 공릉방면 50분(7호선 5 ▶ 경의중앙선 4 ▶ 2호선 12) 둘 다 나온다.
- 검증 6,780개 경로: 최선 유실 0, 라벨 중복 0, 역 되밟기 0, 구간 역<2 0. 선택지 2개 이상인 경우 941 → 2,385.

## 2026-09-22 갱신 초읽기와 스피너, 현재시각 초 단위

- 사용자 지적: "노원 37초 전 / 1분 전"은 불친절하다. 곧 최신화된다는 것이 보여야 한다. 현재시각에 초를 붙이자.
- 구현: `refreshLine()` = 스피너(◐◓◑◒) + `N초 뒤 갱신`. 남은 시간 5초 이하면 두 칸씩 돌아 빨라진다. 갱신 실패 시에만 `갱신 실패 · N초 뒤 재시도`.
- 매초 화면을 다시 쓴다(`TICK_MS = 1000`). 페이지가 이미 텍스트면 `textContainerUpgrade`로 내용만 교체하고, 목록→텍스트 전환 때만 `rebuildPageContainer`를 쓴다(`pageIsText`). tiro 실측대로 upgrade가 가볍다.
- **미실측**: 1초 BLE 쓰기가 안경 배터리에 주는 영향. 빨리 닳거나 쓰기가 거부되면 `TICK_MS`를 2000으로 올린다. 이것이 조절 손잡이다.
- 폴링 렌더와 틱 렌더가 겹치지 않게 `rendering` 플래그를 둔다. `busy` 중에는 틱을 건너뛴다.
- 데이터 나이(`seenAt`)는 지웠다. 신호 끊김 화면의 "마지막 관측 N분 전"만 남긴다. 거기서는 의미가 있다.

## 2026-09-22 사용자 지적 3건: 스피너 품질, 시계 흔들림, 조회 폭주

- **스피너 `◐◓◑◒`는 쓰지 않는다.** 안경 폰트에 글리프가 없으면 조용히 빠져 멈춘 것처럼 보인다(tiro 실측). 실기기에서 보인 것이 확인된 `━ ─`만 쓴다. 회전 대신 **다음 갱신까지 차오르는 막대**로 바꿨다. 뜻이 더 분명하다.
- **전각 글리프는 2칸이다.** 막대 10칸이 20칸을 먹어 35칸으로 넘쳤다. 폭 검사(`ok()`가 `cols ≤ 32`)가 잡았다. 7칸이면 가장 긴 문구까지 31칸이다.
- **초읽기는 두 자리 고정**(`padStart(2)`). 자릿수가 바뀌면 줄이 흔들린다. 막대 줄을 역 이름 줄과 분리했다.
- **초 단위 시계를 보여주면 반드시 움직여야 한다.** 틱을 주행 화면에서만 돌려서 다른 화면은 시계가 멈춰 있었다. `showLive(build)`가 현재 화면의 생성 함수를 `current`에 두고, 하나의 `setInterval`이 텍스트 화면이면 매초 다시 그린다. 목록 화면은 `current = null`.
- **매초 도는 길에서 `log()`를 부르지 않는다.** 한 줄씩 쌓이고 워커로도 날아간다. `textContainerUpgrade` 성공 시 로그 없음.
- **조회 가드를 실제 요청 단위로 옮겼다**(`api.ts get()` 안, `setRequestGuard`). 논리 호출 단위로 세면 도착 조회의 예비 이름 재시도(최대 3번)가 1번으로 보인다. 요청마다 `req path dt=N.Ns mode n` 로그를 남긴다. 다음 폭주는 이 줄이 원인을 가리킨다.
- **주행 화면 탭은 API를 부르지 않는다.** 안내 없는 화면에서 탭마다 도착 조회가 돌았다. 답답해서 누를수록 한도가 샜다. `repickable`이 참인 화면(열차 대기·신호 끊김·못 찾음, 모두 "탭: 열차 다시 고르기"가 적힘)에서만 다시 고른다.
- 미해결: "1분에 10번" 폭주의 실제 원인. 로그 없이는 모른다. 사용자의 진단 기록(`req` 줄)이 필요하다.

## 2026-09-24 경로 이탈·재탐색 (사용자 요청: 환승·이탈 로직 강화, 모두 테스트)

- 순수 판정 `deviation(leg, seen, prev, status, dest)` in route.ts. 실제 노선 데이터로 테스트 10개.
  - 진행 방향: `behind` = 직전 관측이 이웃이면 그것, 아니면(폴링이 역을 건너뜀) 경로 안 이웃. `forward` = 나머지 이웃이 하나일 때.
  - 계속 탈지: `planHop(seen, dest, line, forward)`가 `plan(seen, dest)` + 6분 안이면 `continue`. **하계→홍대입구는 양방향이 46/50분이라 반대로 타도 continue가 맞다.** 시뮬레이터에서 실제로 그렇게 판정했다.
  - 내릴 역: 역에 서 있으면(진입·도착) 지금 역, 떠났으면 `forward`.
  - 사유: `missed`(하차역 이웃 관측 + 직전 관측이 경로 안 → 폴링이 하차역을 건너뛰어도 잡힘) → `diverted`(다른 branch) → `wrongWay`(같은 branch, 직전이 출발역).
- 통합: 구간을 `[지금 역, 내릴 역]`으로 다시 쓰고 뒤에 새 경로를 붙인다. 그러면 **기존 하차 안내→환승 화면→열차 고르기 흐름이 그대로 이어받는다.** 새 코드 경로가 거의 없다.
- 화면: 머리줄 문맥으로 `반대 방향` / `지나침` / `지선 이탈` / `경로 변경`. 같은 노선으로 되돌아갈 땐 `7호선 → 7호선` 대신 `7호선 반대 방향 열차로`.
- 주행 중 탭 = 메뉴(계속 보기 / 현위치에서 재탐색 / 열차 다시 고르기 / 처음으로). 메뉴가 열린 동안 렌더가 덮지 않는다(`menuOpen`).
- 모사 도구: `?api=dev`(/__api → .dev/position.json, .dev/arrival.json), `?poll=fast`(5초), 드라이버 `scratchpad/drv.sh`(pos/arr/tap/shot/launch).
- 시뮬레이터 결과(콘솔 오류 0):
  - S1 하계→홍대입구, 중계방면 탑승 후 공릉 관측 → `continue` → 새 구간으로 즉시 전환, 머리줄 `경로 변경`.
  - S2 하계→노원, 공릉 관측 → `getOff wrongWay at 태릉입구` → 하차 안내 → 환승 화면(반대 방향 열차로) → 자동 탑승 → 노원 도착.
  - S3 노원→하계, 중계 다음 관측이 공릉 → `getOff missed at 태릉입구` → 복구 → 하계 도착.
  - S4 신도림→홍대입구, 도림천 관측 → `getOff diverted at 양천구청` → 복구.
  - S5 메뉴 열림/재탐색(경로 안이면 그대로)/처음으로.
- 미해결: 환승역에 도착한 뒤 사용자가 안 내리고 열차가 계속 가는 경우. 환승 화면에서는 폴링을 멈추므로 못 잡는다. 탭(=내렸다) 전까지는 판단 근거가 없다.

## 2026-09-24 — 0.3.1: 앱이 할 수 있는 일은 앱이 한다 (사용자 교정)
- 교정: "위치가 오래됐습니다 · 직접 고르세요" → "니가 뭔데 사용자한테 시키려고 드냐". 앱은 자기가 할 수 있는 모든 것을 먼저 하고, 정말 아무것도 못 할 때만 묻는다. 화면 문구에 "…하세요/직접 고르세요/탭: 다시 시도"가 보이면 먼저 자동화 여지를 찾는다.
- 출발역: 배너(위치 없음/오래됨/부정확) 삭제. 묵은 위치라도 즉시 후보 목록을 띄우고(거리 앞에 ≈, 지난 도착역 −800m·최근 출발역 −400m 가중), 3초 간격 GPS 감시로 맨 위 후보가 바뀔 때만 다시 그린다(`startOriginWatch`, 3분 뒤 자동 종료). 위치 없음 → 지난 도착역(`lastArrived`, arrive에서 저장) → 최근 출발역 → 자주 가는 곳 순으로 후보를 만든다. 셋 다 없을 때만 안내 화면.
- 탈 열차: 도착 정보 없음/조회 실패/버스트 대기는 초읽기와 함께 자동 재조회(`retryPick`, `pickGen`으로 옛 타이머 무효화). 고른 열차가 피드에서 3번 연속 사라지면 자동으로 다시 고른다(구간당 2번, `autoRepicks`).
- 환승: 타던 열차가 환승역을 떠나면(위치 피드 status 2 또는 다른 역) 다음 구간을 자동 시작(`startTransferWatch`, 20초 폴링, 90초 상한). 문구 "자동으로 다음 열차를 찾습니다 / 탭: 지금 바로".
